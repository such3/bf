# The Journey So Far

A record of how this project went: what was built, every issue that came up, how it was tackled, what the questions were, and what was learned. It is meant for you to re-read, and to show anyone who asks how the project was developed.

**Last updated:** 2026-11-01 (after review #6)

---

## 1. Where it started

**Goal:** learn how compilers, LLVM and computer architecture fit together by building something small enough to see all of it: a Brainfuck (BF) interpreter in C++, growing into an optimizing compiler.

**Starting point:** a single-file interpreter that read one line from `input.txt`, ran it on a 30000-cell tape, matched brackets with a stack and two `unordered_map`s, and printed a trace of its state for every instruction. Most of your debugging history was already written as comments inside the code.

**Direction chosen:** a 10-stage roadmap (see `ROADMAP.md`): harden the interpreter, add phases and an IR, optimize, emit C, assembly and LLVM IR, with a JIT and an MLIR dialect as optional extras.

## 3. Issues and how each was tackled

### Early bugs (before the first review)

| Issue | Root cause | Fix | Lesson |
|---|---|---|---|
| Printing a cell showed characters, not numbers | `cout << unsigned char` picks the character overload | Cast to `(int)` for the cell and `(int)(unsigned char)` for program characters | Know which overload you are calling |
| `[` jumped to the wrong place | Looked up the map with `tpptr` instead of `strptr` | Use the position in the program text | A map's key type is part of its meaning |
| `]` corrupted later jumps | `revpos[strptr]++` modified the stored value | Read the value, then add 1 | `++` writes; use `+ 1` to read |
| `>` printed the same character forever | `strptr` was never advanced | Advance `strptr` in every case | Every instruction must advance or jump |
| Matching brackets failed | Missing `continue` after a matched `]` made control fall into the error path | Added it. (The `continue` after `push` is not needed; CLEAN-1) | Read control flow, not just conditions |
| Tape overflow never detected | Compared the iteration counter instead of `tpptr` | Compare the pointer | Check the variable that represents the limit |

### Issues found by reviews

| ID | Issue | Root cause | How it was tackled | Lesson |
|---|---|---|---|---|
| Input | Only the last line of the program survived; an empty string could result | `getline` clears its target on every call, including the final failing one | Read each line into `rdLine` and append to the program text | Separate "current line" from "everything so far" |
| Brackets | Stray `]` ignored; unclosed `[` unnoticed | No validation | Report both cases before running | Validate input before executing it |
| BUG-1 | `<` at cell 0 hung forever | `break` inside a `switch` left the switch without advancing `strptr` | Advance `strptr` before the `break` | `break` leaves the nearest enclosing loop or switch |
| BUG-2 | Errors reported success to the shell | `exit(0)` | `exit(1)` for failures; overflow also exits 1 | Exit status 0 means success; scripts depend on it |
| BUG-3 | Missing file went unnoticed | Stream state never checked | `is_open()` check; `peek() == EOF` for a 0-byte file | Check whether a resource was acquired |
| BUG-5 | Crash with no arguments | `argv[1]` used without checking `argc` | `argc < 2` check | `argv[argc]` is a null pointer |
| BUG-7 | Programs with comments or spaces failed | The check used `\|\|` (always true), looked at the wrong index, contradicted the language, and sat in the wrong layer | Studied the truth table, then the language definition; concluded other characters are comments and skip them | Understand the rule before writing the check; write the failing test first |
| Structure | Eleven copy-pasted trace blocks | Variables spread over `main` | Group state in a struct; one `dumpState(const&)` | When variables travel together, they are one type |
| Rename | Comments and a printed string had changed | "Change all occurrences" is text replacement | Reverted by hand; learned to rename symbols and read the diff | A text replace cannot tell code from comments from strings |
| Duplication | The program text existed twice | Read into a buffer, then copied into the struct | Append straight into the struct | One home per piece of state |
| Trace lag | The last instruction's effect was never shown | The trace prints state before each instruction | Added a final dump after the loop | Know exactly when your trace samples the state |

## 4. Questions you asked, and where they led

| Question | Short answer | Where |
|---|---|---|
| How do I tell how I'm doing, and is this learning working? | Yes: you fix bugs your own way, research and record conclusions, and ask the right next questions. The weak spot is testing edge cases before calling a change done | Progress discussion |
| Where should I look up doubts, and is asking AI okay? | Yes, with a routine: read the message, run a tiny experiment, check primary sources, then ask with your attempt; verify what you are told | "Doubt ladder" reply |
| How does a logging function access `main`'s variables? | Group them in a struct at file scope; pass by `const` reference; keep the struct as the real home of the variables, not a copy | Struct discussion |
| Can I use exception handling for errors? | Yes, as a mechanism with trade-offs. Use it for rare serious errors found deep in a call chain. LLVM and MLIR do not use exceptions, so also learn value-or-error style | Review #3b |
| Why do we need LLVM here? | You do not; it enters at Stage 7 to avoid writing a backend per CPU, to get a mature optimizer, and because real compilers sit on it | LLVM reply |
| If the interpreter works, why a compiler? | A compiler does the decoding once instead of on every instruction, enables whole-program optimization, and ships a binary | Compiler reply |
| What is an invalid Brainfuck program? | Only mismatched brackets are a syntax error; everything else is a comment, an implementation limit, or a valid no-op | BUG-7 discussion |
| Is internship value in this project? | A toy on its own, but real depth if polished, benchmarked and followed by real contributions | Internship reply |
| What is stdout vs stderr? | Still to finish: the experiments are in review #3 section 5 | Open |

## 5. Decisions made

| Decision | Choice | Reason |
|---|---|---|
| Tape | 30000 cells, 8-bit unsigned, wraps | BF convention; wraparound is well-defined |
| Moving past the right end | Stop with an error and exit 1 | Continuing would corrupt memory |
| Failures | Exit status 1 | 0 means success; tests and scripts need a failure signal |
| Source files | Taken from the command line (`argv[1]`) | Replaces the hard-coded `input.txt` |
| Multi-line source | Lines concatenated | Simple; loses line numbers (revisit in Stage 1) |
| Non-command characters | Skipped as comments | That is what the language specifies |
| Program text | Stored in the machine-state struct | One home; revisit when Stage 2 introduces an IR |
| Commit hygiene | Code and docs in separate commits; messages state known issues | Keeps history honest |

**Still undecided:** what `<` at cell 0 should do (DEC-1), exit codes per error category (DEC-3), whether 0-byte, whitespace-only and comment-only files differ (DEC-5), extra command-line arguments (DEC-8), the error-handling mechanism (DEC-10), and a future strict mode (T-12).

## 6. Concepts you have worked through

- **Stack-based matching** and why it handles nesting without special cases
- **Jump semantics** of `[` and `]`, and why landing one past the bracket is equivalent to re-testing
- **`unsigned char`**: wraparound, integer promotion, and the `cout` overload
- **`getline` behavior** at end of file
- **Exit status** and the shell's `$?`
- **`argc` and `argv`**, and the null terminator of `argv`
- **`switch` and `break`** semantics inside loops
- **`||` vs `&&`** and De Morgan's laws, through a truth table
- **Passing by `const` reference**, and why large state should not be copied
- **Structs as state**, the "home vs copy" distinction, default member initializers
- **Interpreter vs compiler**; your interpreter as a tiny virtual machine (program counter, data pointer, memory, fetch-decode-execute)
- **Why LLVM exists**, and the shape of the remaining stages

## 7. Habits you built

1. **Writing questions down** the moment they appear, then answering them.
2. **Stable IDs** for bugs, to-dos, decisions and questions (`BUG-7`, `DEC-9`), referenced from code and commits.
3. **Dated reviews** instead of editing one document, so progress is visible.
4. **Experiments before explanations**: run it, predict, observe.
5. **Before/after `diff`** of program output around refactors.
6. **Write the failing test first** (the `+++ hello` case for BUG-7).
7. **Commit messages** that say what changed and what is still broken.
8. **Comment conventions**: `NOTE:` for why, `TODO(ID):` for open work, history in git and the tracker.

## 8. Patterns worth watching

These came up more than once, so they are the useful lessons:

| Pattern | Examples | Counter-habit |
|---|---|---|
| A fix introduces a new bug | `<` guard hang; `argv` crash; the unsupported-character check | Test edge cases and the neighbours of what you changed, before calling it done |
| Advancing the program counter | `>` forgot it; `<` skipped it | Every instruction must advance or jump |
| Success reported on failure | `exit(0)`; overflow `return 0` | Check `echo $?` for every failure path |
| Mechanical edits touching more than intended | "Change all occurrences" | Rename symbols; read `git diff` |
| Stale comments and TODOs | `TODO(BUG-5)` after the fix; "UNRESOLVED BUG" text | Delete a TODO in the same commit that does the work |
| Two sources of truth | Two maps; two copies of the text | Give each fact exactly one home |

## 9. Where the code stands today

**Works:** all eight commands (`,` is skipped), nested loops, comments and whitespace in programs, cell wraparound, multi-line files, argument and file checks, bracket validation, tape-end detection, a state struct with a single trace function, a final state dump.

**Known gaps:**

- No automated tests (T-3)
- The trace is always on and mixed into the program's output (T-2, BUG-4)
- Errors go to `cout`, not `cerr` (BUG-2)
- No step limit (T-4)
- `,` not implemented (T-10)
- `<` at cell 0 is silently ignored (DEC-1)
- Stale comments, an unused variable, and unclear names (CLEAN-8, CLEAN-9, CLEAN-11)
