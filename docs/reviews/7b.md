## 3. Issues

### T2-6 (Medium): the argument dump still misbehaves

```cpp
for (int i = 2; i < argc; i++)
{
    if (verboseOn)
        cout << "Arguement " << i << " : " << argv[i] << endl;
    ...
    if (arguement == verbose) { verboseOn = true; ... }
}
```

I ran three cases:

| Command | What happened |
|---|---|
| `./bf f.bf --verbose` | No `Arguement` line at all |
| `./bf f.bf --verbose extra` | `Arguement 3 : extra` printed on **stdout**, before the program's `F` |
| `./bf f.bf --verbose --verbose` | `Arguement 3 : --verbose` printed on stdout |

Questions:

- At the moment the `if (verboseOn)` runs for the flag itself, what is the value of `verboseOn`? What does that say about which arguments can ever be printed?
- This is the only trace line that uses `cout`. What does that do to the program's output?
- Where would the dump have to run so that the flag is already known? Should it list *all* arguments, including `argv[0]` and `argv[1]`, or only the ones after the path?

### T2-7 (Medium): the interpreter adds a byte to the program's output

```cpp
cout << endl;
return 0;
```

| Program | stdout bytes |
|---|---|
| `+++++++[>++++++++++<-]>.` (prints `F`) | `F` then `\n` |
| `++++++++[>++++++++<-]>+.+.` (prints `A`, `B`) | `A` `B` `\n` |
| `+` (prints nothing) | `\n` |

Your comment calls it "the final new line after everything has already been printed". Think about who owns the output:

- A Brainfuck program decides every byte it writes. If it wants a newline, it prints value 10. Whose job is the extra one?
- What would `./bf prog.bf | wc -c` report for the third program? What would a test that compares output exactly have to expect?
- When the program exits through an error, the newline is not printed. Is "sometimes added" better or worse than "never added"?
- What does your shell do if the output does not end in a newline? Is that the interpreter's problem?
- Output is flushed at exit regardless, so you do not need the `endl` to flush.

### DEC-12 (decision needed): `clog` or `cerr` for the trace

With `./bf f.bf --verbose 2>&1`, I looked at where the program's `F` landed:

```
663: Final Dump state
665: F
```

The program's output appears **after** the whole trace, even though the program printed it long before.

- `cout` is buffered and is only flushed at exit here. `clog` is not tied to `cout`, so writing to `clog` does not flush it. What is different about `cerr`? (Look up `tie()` and `unitbuf`.)
- Would you prefer the trace and the output interleaved in the order things happened, or is "trace first, output last" fine for your debugging?
- If you choose `cerr`, would anything else change? (Think about what the tie costs when a lot of trace is printed.)
- Write the decision down as DEC-12, with the reason.

### T2-5 (rest of it)

- The usage line in the header comment now says `[--verbose]`, but no code prints a usage message. When `argc < 2`, should the error show how to run the program?
- "Error in opening file" does not say **which** file. What would help someone who typed `./bf --verbose f.bf` and got that message?
- `./bf f.bf --verbos` (a typo) is silently ignored. That is DEC-8. Is silence what you want?

### REF-5 (still open)

The last line of the trace is still `... String Content : 0`, which is the string's terminating `\0` at index `length()`. Review #6 listed three designs. Pick one; the stream is already settled.
