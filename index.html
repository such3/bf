From a tiny Brainfuck interpreter to a compiler path

This project started as a simple C++ interpreter and is now a real learning project about compiler design, runtime behavior, error handling, and later backend work.

Read the full write-up GitHub

What we built so far

Interpreter core

Reads a Brainfuck source file, validates brackets, runs the tape machine, and handles the main command set.

Runtime guardrails

Protects the tape from overflow, checks left-bound movement, and keeps the program state visible in verbose mode.

Compiler roadmap

The project already points toward separate phases, an IR, optimization passes, and later C / assembly / LLVM backends.

Current status

Verified behavior: Running ./run input.txt --ver currently prints the help text and then hits the left-bound tape error.

What the project is teaching

  • How a tiny virtual machine is built from a program counter and tape
  • Why bracket matching and jump targets matter before runtime
  • How error handling, exit codes, and stream separation really work
  • Why a compiler needs phases, an IR, and optimization passes later on

Important code pattern

while (static_cast<size_t>(machine.pc) < machine.program.length()) {
    if (machine.data_ptr == 30000) {
        cerr << "[OVERFLOW] Tape overflow !!\n";
        exit(1);
    }

    switch (machine.program[machine.pc]) {
        case '<':
            if (machine.data_ptr == 0) {
                cerr << "[ERROR] Access out of tape bounds\n";
                exit(1);
            }
            machine.data_ptr--;
            machine.pc++;
            break;
    }
}

Biggest difficulties

Pointer bugs

The most common issue was forgetting to advance the program counter or misreading the tape pointer when a jump was triggered.

Bad early assumptions

Some problems came from thinking the program could just skip invalid characters without deciding what represents a real Brainfuck program.

Output vs debug

Separating real BF output from trace logs was a real design issue. The program output belongs to stdout; debug output belongs to the trace path.

CLI hardening

Flags, missing files, and unsupported arguments still need a cleaner, more deliberate policy instead of ad hoc checks.
