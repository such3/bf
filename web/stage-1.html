Stage 1: Building and hardening the interpreter

This is the current stage of the project: a working file-based Brainfuck interpreter, a set of runtime guardrails, and a clear roadmap toward compiler backends.

What the interpreter does

The project is a tiny virtual machine made of a program counter, a data pointer, and a tape of byte cells.

Machine model

  • Program counter tracks the current instruction
  • Data pointer moves across the tape
  • 30000 byte cells hold the Brainfuck state
  • Brackets are validated before execution

Supported commands

  • + - increment and decrement
  • < > move the tape pointer
  • . output the current cell
  • [ ] loop instructions

What was hard

Pointer mistakes

Forgetting to advance the program counter was a classic bug. The same instruction would loop forever because the interpreter never moved past it.

Jump logic

Bracket jumps had to be keyed by program position, not tape position. The wrong key produced incorrect loop behavior.

Output separation

Program output and debug tracing had to be separated to avoid polluting the actual Brainfuck output.

Current runtime issue

The latest run of ./run input.txt --ver still ends with the left-bound tape error. This is the current known runtime behavior.

Core execution pattern

while (static_cast<size_t>(machine.pc) < machine.program.length()) {
    if (machine.data_ptr == 30000) {
        cerr << "[OVERFLOW] Tape overflow !!\n";
        exit(1);
    }

    switch (machine.program[machine.pc]) {
        case '<':
            if (machine.data_ptr == 0) {
                cerr << "[ERROR] Access out of tape bounds\n";
                exit(1);
            }
            machine.data_ptr--;
            machine.pc++;
            break;
    }
}

Project decisions

Error handling

Runtime failures use exit status 1. This is a deliberate choice so scripts can tell whether the program actually failed.

Verbose mode

The interpreter supports --verbose for debugging. Unsupported flags still print help while the CLI is being hardened.

Comments and non-commands

Anything outside the Brainfuck instruction set is treated as a comment and skipped.

Next improvement

The next large work is to separate loading, validation, and execution into clearer phases.

Why this matters

This is not only a toy interpreter. It is a small compiler-learning project. The interpreter gives a direct view of machine state, loop semantics, and runtime errors before moving into optimization and code generation.
